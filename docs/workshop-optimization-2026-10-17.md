# Анализ и оптимизация оформлений мастерской

Устройство из сообщения пользователя: Samsung Galaxy S24 Ultra. Физический телефон к этой среде не подключён. Измерения получены на изолированном Android API 36: отдельно на SwiftShader и отдельно с графическим драйвером NVIDIA компьютера. Их нельзя выдавать за FPS или задержки Galaxy S24 Ultra.

## Охват

Проверены пути использования всех 26 товаров каталога: 6 тем карточек, 3 оформления краёв, 5 фонов, 6 стилей связей, 3 оформления виджетов и 3 рамки экспорта. Первые 20 товаров участвуют в непрерывной отрисовке дерева. Рамки виджета и экспорта рисуются при создании соответствующего bitmap/страницы, а не для каждого человека на каждом кадре дерева.

Матрица дерева: стандартное оформление, каждый из 20 товаров отдельно, три тематических сочетания и четыре смешанных сочетания. Для всех 28 пар «тема карточки × оформление краёв» предусмотрена отдельная проверка наличия всех 500 карточек. Дополнительный сценарий использует 500 отдельных синтетических фотографий. Это покрытие всех товаров и важных взаимодействий, а не перебор каждой возможной комбинации настроек и размеров окна.

Навигация выполнена через индекс codebase_memory с подтверждением в исходниках: RewardCatalog → MainActivityWorkshop.applyWorkshopStyles → TreeCanvasView.drawScene/drawCards/drawStyledLink. Проверены также FireCardEffect, SmokeCardEffect, BotanicalEffect, BotanicalCanvasBackground, PaperTexture, BirthdayWidgetRenderer и ExportDecoration.

## Найденные причины и исправления

| Причина | Изменение |
|---|---|
| Огонь и дым создавали десятки тысяч отдельных команд GPU для 500 карточек, включая кривые, трансформации и частицы. | На плотном интерактивном дереве полные эффекты рисуются в атласы. Первый атлас прогревается программно, последующие готовит отдельный поток; главный поток рисует готовые изображения. Малое число видимых карточек и экспорт используют исходный процедурный путь. |
| Ленточные связи заново измерялись и строили синусоидальные дорожки на каждом кадре. | Геометрия всех контуров хранится в мировых координатах и переживает перемещение и масштабирование. Родственные пунктиры, оба переплетённых контура и короткие сегменты сохранены. |
| Семейные связи в цвет карточек создавали новые Path и Relation для каждого владельца каждый кадр. | Части маршрута кэшируются до изменения семейного плана или режима линий. Цвет берётся из актуального человека. Градиенты индивидуальных связей пересоздаются при изменении координат или цветов. |
| Растительный кэш целиком сбрасывался после 1024 связей, что могло повторяться каждый кадр. | Кэш геометрии привязан слабыми ключами к существующим путям, ограничение bitmap по байтам сохранено. Отдельная проверка использует 1200 связей в двух последовательных кадрах. |
| Bitmap длинной растительной связи ограничивалась шириной 4096, после чего обрезанная часть растягивалась на полный маршрут. | Непомещающаяся целиком связь использует полный записанный векторный путь. Проверяется последний вертикальный сегмент маршрута длиной более 6000 единиц. |
| Ключ растительных краёв использовал seed & 7, хотя рисунок зависит от seed & 255. | Различные исходные варианты листьев больше не смешиваются. Проверка сравнивает два seed с одинаковыми младшими тремя битами. |
| Растительные изображения всегда занимали bitmap в масштабе не меньше 1:1 мировых единиц, даже при отображении в десять раз меньше. | Все стебли, прожилки и цветы сначала рисуются в кэш с плотностью не ниже экранной. При близком увеличении используется полный вектор. Никакие элементы по расстоянию не исключаются. |
| Статичные дымные и растительные рисунки поверхности повторно рисовались для каждой карточки. | Добавлен ограниченный кэш полных рисунков. Для дыма сохраняются все используемые исходником углы; растительный рисунок поверхности не зависит от seed и разделяет одну запись. |
| Темы создавали множество одинаковых Shader и строковых ключей, а даты и места повторно измерялись. | Градиенты заливки/стекла/полуночной темы переиспользуются, метрики шрифта и ширина метаданных кэшируются. Размеры кэшей учитывают число людей, чтобы большое дерево не сбрасывало их каждый кадр. |
| Фоновый градиент мог наследовать прозрачность Paint от последней карточки предыдущего кадра. | Прозрачность фона задаётся явно; проверяются одинаковые кадры после разных входных значений Paint. |
| Растительный фон декодировался при создании любого TreeCanvasView, включая не использующие этот фон. | Текстура загружается при первом использовании и разделяется между рендерами с одинаковой плотностью ресурсов. |
| На снимке сильно отдалённого дерева проявились резкие стыки растительного фона: исходная фотографическая текстура не бесшовная. | Обе текстурные фазы повторяются зеркально, сохраняя исходное изображение. Новый тест обнаруживает горизонтальный стык старой сборки (средний скачок RGB 12,71) и проверяет непрерывность обеих границ после исправления. |
| Запас отрисовки в 520 экранных пикселей заставлял обрабатывать далеко заэкранные карточки. | Используется консервативный запас по фактическим размерам эффектов и экранных обводок. Все видимые карточки и выступающие части оформления сохраняются. |

## Гарантии и ограничения нового пути

Атласы используют исходные FireCardEffect/SmokeCardEffect, исходный seed и единое время для всего кадра. Они не объединяют людей в несколько декоративных вариантов, не сокращают частицы, не выключают края и не убирают содержимое при отдалении. Раздельные слои за карточкой и перед текстом сохраняют порядок отрисовки.

Плотность подготавливаемого изображения округляется вверх относительно масштаба. Вокруг ячеек есть прозрачный отступ и дополнительный gutter против проникновения соседнего изображения. Пока увеличенный атлас готовится, может отображаться предыдущий полный кадр с интерполяцией; текст и фотографии карточек от него не зависят. Новый человек, вошедший в экран во время перемещения, получает полный временный рисунок до поступления нового атласа. При невозможности уложиться в бюджет остаётся исходная полная векторная отрисовка.

Размер одного полного атласа ограничен меньшим из 16 МиБ и 1/12 доступного heap, с минимумом 2 МиБ. Существует только одна фоновая задача; очередь кадров не накапливается. Смена оформления и закрытие окна отменяют устаревшую работу. Отображавшиеся bitmap не вызывают recycle, поскольку их ещё может использовать RenderThread. Первая подготовка тяжёлого оформления остаётся синхронной; приведённые ниже тёплые аппаратные замеры её не включают.

Проверка обычного масштаба выявила лишний расход памяти в первой реализации: плотность 0,55 округлялась до 1, а передние обводки получали такие же широкие пустые поля, как задние облака. Финальная упаковка округляет плотность вверх шагом 1/16, сохраняет полный задний эффект с полем 48 мировых единиц и передние обводки с полем 16. Поля покрывают реальные границы исходных эффектов; их начало совпадает с пиксельной сеткой при выбранных плотностях. Например, для 64 карточек 280×160 при масштабе 0,55 два слоя занимают 14 595 840 байт вместо 67 370 240 байт. Это позволяет использовать атлас на обычном масштабе без снижения разрешения ниже экранного. Сравнение с процедурным рендерером расширено до четырёх плотностей и трёх моментов анимации.

Этот лимит относится к одному кадру атласа, а не ко всей памяти процесса: одновременно могут существовать показываемый, опубликованный и подготавливаемый кадры, временные рисунки вошедших карточек и изображения, ещё удерживаемые RenderThread до сборки мусора. Статичные поверхности имеют отдельный LRU-бюджет до 8 МиБ, растительные bitmap — до 32 МиБ. Системное уведомление об уменьшении доступной памяти освобождает эти графические кэши.

Регрессионная проверка выявила устаревание цветного семейного маршрута после прямого изменения координат человека. Добавлена недорогая проверка координат перед использованием семейного плана: при перемещении путь пересчитывается, при обычном панорамировании остаётся в кэше. Исправление подтверждено повторным прохождением обоих тестов цветных связей и всего набора из 36 инструментальных проверок.

PNG/PDF продолжают использовать фиксированный момент времени и исходный процедурный рендерер. Внешний вид виджетов и рамок экспорта не упрощался.

## Измерения и проверки

Исходная программная матрица на 500 карточках полностью завершена: 24 варианта, один холодный кадр и пять повторных измерений. Например, медиана сочетания огня — 416,97 мс, дым + ленты — 252,42 мс. Это стоимость программной растеризации на компьютере внутри эмулятора.

Исходный аппаратный прогон с 32 кадрами остановился на огненных краях с ANR. Лог сохранён. Для сопоставимого контроля остальные 22 варианта повторены по 16 измеренных кадров после шести прогревочных. Тяжёлые огненные края и их сочетание повторно не запускались в исходной версии после зафиксированного ANR.

Основной прогон оптимизированной версии прошёл **28 аппаратных и 28 программных сценариев**, `OK (2 tests)`, 190,449 с. Аппаратная проверка после каждого сценария утверждает наличие всех **500 видимых карточек**. Для сравнения — по 16 измеренных кадров после шести прогревочных в одном и том же эмуляторе, без параллельного Gradle. Дерево содержит 500 людей, 475 родительских и 100 связей братьев/сестёр; масштаб 0,1. Геометрия и содержимое сохраняются целиком. Этот прогон предшествует финальным изменениям упаковки атласа и стыков фона; их отдельные проверки приведены ниже.

Это **не одинаковое улучшение всех показателей**. Полное растительное сочетание по DRAW практически не изменилось; его TOTAL снизился с 829,03 до 634,52 мс. В сочетании «дым + ленты» DRAW снизился, но TOTAL вырос с 650,93 до 802,05 мс; у отдельных дымных краёв — с 568,54 до 683,70 мс. Растеризация атласов в рабочем потоке может конкурировать с программным SwiftShader за CPU; это объяснение требует проверки на физическом GPU. Исправление растительного seed возвращает ранее потерянные варианты рисунка. Без физического GPU нельзя заключить, что FPS каждого оформления улучшился. Полные результаты всех 28 сценариев, включая p95 и TOTAL, приведены в `comparison.csv` и JSON.

Снимки PSS после отдельных сценариев составили 167 213–222 954 КиБ; это не измерение пикового потребления и не сравнение памяти до/после. Программный экспорт сохраняет исходный процедурный путь: медианы огненного сочетания 416,97 → 418,19 мс, дыма с лентами 252,42 → 262,28 мс, растительного сочетания 102,57 → 83,10 мс. Результат не объявляется ускорением всех экспортных оформлений.

Проверки корректности: **342 модульных теста**, 0 ошибок; **36 инструментальных тестов**, 0 ошибок, 179,491 с; lint **0 ошибок, 155 предупреждений**. Инструментальные проверки включают все 28 пар тем/краёв на 500 людях, попиксельное сравнение атласа с исходными эффектами при трёх плотностях, 1200 растительных связей без циклического сброса, длинный маршрут, разные seed, цвета и перемещение семейных связей, PNG/PDF и декоративные рамки. Допуск сравнения учитывает только округление premultiplied alpha; он не разрешает пропажу деталей.

После правки стыков и упаковки атласа повторены все **7 графических тестов WorkshopRenderingTest**, успешно, 11,692 с, включая новый тест непрерывности фона и расширенное сравнение четырёх плотностей в трёх фазах анимации. Повторная сборка, 342 модульных теста и lint также успешны. Новый тест стыков сначала отдельно запускался на старом APK и завершился ожидаемым отказом, поэтому он проверяет реальный дефект.

Дополнительный аппаратный прогон с **500 отдельными загруженными фотографиями** прошёл все четыре случая (`OK (1 test)`, 39,723 с): стандарт, полный огонь, дым/ленты, растительное сочетание. Медианы DRAW: 25,10 / 54,69 / 65,06 / 80,96 мс. PSS после сценариев: 184 328–233 262 КиБ. Это новый контроль нагрузки, сравнения с исходной версией с фотографиями нет. Фотографии синтетические, 64×64, поэтому результат не описывает холодную загрузку 500 исходных многомегапиксельных файлов.

Все исходные JSON и журналы — в `performance-audit-2026-10-17/workshop-stage4/`. Медианы DRAW_DURATION описывают работу главного потока при формировании кадра; TOTAL_DURATION зависит также от SwiftShader и ожидания графического конвейера. Процентили небольших контрольных выборок не заменяют длительного профилирования на телефоне.

Для воспроизведения используется `WorkshopPerformanceTest`: аргумент `workshopFrames=16`, без фильтров для полной матрицы. `workshopPhotos=true`, `workshopLabel=photos` и `workshopOnly=standard,all-fire,all-smoke-ribbon,all-botanical` включают четыре сценария с 500 отдельными синтетическими фотографиями; измерение начинается только после загрузки всех 500. Снимок шести исходных графических классов и Gradle init script для контрольной сборки сохранены в `baseline-source.zip`. Контрольная сборка подменяет только компиляционные входы, не откатывая рабочие исходники.

## Проверка R8 и графического окружения

Изолированный R8-вариант с финальным атласом прошёл **все 5 smoke-тестов одним прогоном**, 26,888 с: запуск, оба языка, каталог и галереи, файлы, PNG-предпросмотр, настройки, мастерская, дерево из 500 людей с огненной темой/краями и галерея 500 фотографий. Тесты используют публичные Android API без ссылок/reflection во внутренние классы приложения, поэтому не добавляют keep rules для проверяемых реализаций. Это отдельный debug-подписанный вариант с demo-рекламой и отключённой отправкой аналитики, а не подмена производственной конфигурации.

Два предыдущих запуска этого сценария на SwiftShader завершились нативным падением процесса эмулятора Windows `qemu-system-x86_64-headless.exe`, код 0xc0000005; записи событий сохранены в `emulator-native-crashes.json`. Смена графического режима на `-gpu host` позволила завершить проверку. В первом запуске на host также зафиксирован тайм-аут ожидания стартового интерфейса; отдельный запуск прошёл, затем после финальной упаковки атласа успешно прошёл весь набор из пяти тестов. Эти промежуточные сбои не объявляются успешными проверками. Повторение на физическом Android остаётся необходимым для оценки совместимости конкретного драйвера.

Для host используется тот же API 36 и экран 1080×2400, графический драйвер NVIDIA GeForce RTX 4060 Laptop GPU.
