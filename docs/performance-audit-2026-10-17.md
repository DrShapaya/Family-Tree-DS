# Анализ производительности Family Tree DS

Дата: 17 октября 2026. Проверена текущая рабочая копия AndroidFT 2.0. Это план улучшений по исходникам и локальным экспериментам, а не отчёт о замерах FPS на устройстве. На момент аудита производственный код не изменялся. Реализация последующих исправлений описана в `optimization-implementation-2026-10-17.md`. Сайт AndroidFT-site не проверялся; встроенный HTML-экспорт проверен.

**Условие всех рекомендаций:** сохранять людей, подписи, даты, фото, линии, оформление, записи и вложения. Отдаление дерева не должно включать режим с исчезающим содержимым. Ускорение достигается повторным использованием результатов, более подходящими алгоритмами, выполнением тяжёлых задач вне UI и устранением лишней работы.

## Что уже сделано правильно

- У карточек есть пространственный индекс, у текста и геометрии линий — кэши.
- Фото из TreeMediaStore декодируются для холста в отдельном потоке.
- Основной файл записывается через AtomicFile, версии пишутся отдельным исполнителем.
- .ftree хранит бинарные вложения отдельно от JSON, медиа копируются потоково.
- Полная ручная раскладка в MainActivity запускается в рабочем потоке.
- PDF использует отдельный TreeDocumentRenderer в рабочем потоке.
- При онлайн-проверке применяется ETag; медиа адресуются по содержимому.
- BotanicalEffect уже кэширует геометрию и имеет записанный векторный fallback. Повторно изобретать такой же кэш не требуется.

Имеющиеся механизмы стоит доработать. Полная смена Canvas на другой движок или переписывание всего приложения пока не обоснованы измерениями.

## Локальные замеры

Измерены Java-операции в JVM 21.0.10 на компьютере через classpath модульных тестов. По 2 прогревочных и 5 измеряемых вызовов, в таблице медианы. Синтетическое связное дерево: одна родительская связь для каждого человека после корня, имя, дата, место, биография примерно на 800 символов и одна запись памяти. Размеры: 500, 2000 и 5000 человек.

Android API представлены тестовыми заглушками, JSON — зависимостью модульных тестов. Время диска, GPU, Android View, загрузки фотографий и сети здесь не измерено. Это диагностический эксперимент, не JMH, Macrobenchmark или прогноз скорости на смартфоне. Небольшие результаты копирования особенно чувствительны к JIT/GC и порядку прогрева.

## 1. Отрисовка: убрать полный обход дерева из проверки кэша

**Высокий приоритет.** `TreeCanvasView.familyLinePlan()` каждый кадр заново вычисляет подпись: проходит всех людей, координаты, пол и все связи. При неизменном дереве панорамирование всё равно несёт стоимость O(N+E) до использования готового плана. Затем drawLinks отдельно проходит маршруты и список связей.

Код: `TreeCanvasView.java:788`, `:854`.

Улучшение: ввести отдельные ревизии структуры, координат, параметров карточки и фильтра. Ключ плана — набор этих ревизий. При чистом перемещении камеры проверка становится O(1). Для изменения координаты обновлять затронутые маршруты и их bounding boxes. Для видимых линий добавить пространственный индекс, аналогичный индексу карточек.

Границы маршрутов должны включать изгибы, декоративные элементы, толщину линии и выделение. Линия может пересекать экран, когда обе карточки находятся снаружи: выбирать её только по видимости концов нельзя.

**Содержание:** все пересекающие экран элементы остаются. При отдалении, когда видно всё дерево, рисуются все карточки и линии. Пространственный индекс ускоряет выбор, не заменяет содержимое.

## 2. Отрисовка: не пересобирать строки и графические объекты в кадре

`cardMeta()` перед попаданием в кэш вызывает `PersonNames.display()` и `PersonNames.search()`. Те используют регулярные выражения, разбор имён и новые строки. Ключи кэшей переноса имён тоже собираются строковой конкатенацией. `cardFillGradient()` создаёт LinearGradient для карточек, а некоторые стили линий — PathMeasure и массивы координат при рисовании.

Код: `TreeCanvasView.java:1908`, `:2101`, `:2130`, `:3038`, `:1215`; `PersonNames.java:5`.

Улучшение: подготовленный CardRenderData по ревизии человека; готовые подписи, переносы, инициалы и метаданные. Геометрию и градиенты хранить в локальных координатах карточки, при движении применять матрицу. Повторно использовать RectF, Path, FontMetrics и массивы там, где их время жизни позволяет это безопасно.

Не начинать с глобального object pool или переписывания всех циклов: приоритет — объекты и преобразования, реально создаваемые для каждой карточки каждого кадра.

## 3. Кэши: устранить вытеснение по кругу и полные очистки

В TreeCanvasView фиксированные ёмкости: 640 записей переноса имён, 960 сокращённых имён, 1200 CardMeta. Если на экране тысячи уникальных карточек, последовательный обход может вытеснять данные прежде, чем они понадобятся в следующем кадре. Для фото есть бюджет 8–32 МБ; ключ включает person.id, поэтому одно mediaId у разных людей декодируется/учитывается отдельно.

Код: `TreeCanvasView.java:86`, `:179`, `:1998`, `:2031`.

Улучшение: дешёвые текстовые метаданные хранить с моделью представления/по ревизиям, а не в маленьком LRU; тяжёлые bitmap — в общем кэше по mediaId и размеру декодирования. Кадрировать общую bitmap по параметрам человека при рисовании. Для производных размеров использовать реальный размер фото в пикселях текущего вида; при приближении и экспорте брать достаточное разрешение. Оригиналы остаются неизменными, фото не исчезают на дальнем масштабе.

При изменении одного человека инвалидировать его данные и связанные маршруты. `setState()` при новой ссылке на TreeState сейчас сбрасывает кэши целиком, хотя синхронизация могла изменить одну запись.

Для повторного использования bitmap и бюджетирования по памяти подходит описанный Android подход к [кэшированию bitmap](https://developer.android.com/topic/performance/graphics/cache-bitmap). Конкретные бюджеты следует выбирать по замерам устройств, а не просто увеличивать все кэши.

## 4. Фото: управлять очередью декодирования

`schedulePhotoDecode()` умеет объединять одинаковый ключ, но очередь однопоточного исполнителя не ограничена и не переприоритизируется по новой области просмотра. Быстрая навигация может оставить в очереди много уже неактуальных фото. Каталог использует отдельные два потока и кэш на 48 bitmap по количеству, не по байтам; незавершённые одинаковые запросы там не объединяются.

Код: `TreeCanvasView.java:2027`; `MainActivityPeople.java:77`, `:2433`.

Улучшение: общий загрузчик с объединением in-flight запросов, приоритетом текущего экрана, отменой устаревших задач и проверкой ревизии перед установкой результата. Ограничить одновременно декодируемый объём памяти и размер очереди. Объединять поступившие результаты в одно обновление кадра. Освобождать только воспроизводимые кэши, не оригиналы.

Особенно важно для общего вида большого дерева: фиксированное декодирование каждого портрета в 192 px может постоянно заполнять очередь и вытеснять результаты, когда физический размер портрета на экране намного меньше.

## 5. Эффекты и анимации: повторно использовать статическую часть

Огонь и дым инициируют перерисовку сцены; подсветка пути тоже вызывает новые кадры. Огонь выполняет много геометрических операций на каждую карточку. Растительная тема уже имеет кэш и записанный векторный fallback.

Код: `TreeCanvasView.java:1466`, `:1555`; `FireCardEffect.java:23`; `BotanicalEffect.java:17`.

Улучшение: разделить статическую геометрию, текст и фото от меняющейся фазы эффекта. Для неизменных частей исследовать записанные команды Canvas/RenderNode с учётом API устройства. Планировать один кадр общим планировщиком, не выполнять связанные проверки модели заново из-за декоративной анимации. Пауза допустима, когда окно приложения действительно не видно; масштаб не должен отключать эффект.

Не кэшировать всё дерево одной bitmap недостаточного разрешения: это заменило бы вычислительную проблему размытием текста. Нужны независимые записи/кэши с сохранением разрешения.

## 6. Каталог и галереи: переиспользовать строки вместо построения всех View

**Высокий приоритет.** Каталог — ScrollView + LinearLayout. При фильтрации `fillPeopleRows()` удаляет все строки и создаёт новые для всех найденных людей. Затем на каждую строку приходится создание дочерних View и работа с аватарами.

Код: `MainActivityPeople.java:324`, `:504`, `:529`, `:2433`.

Улучшение: [RecyclerView](https://developer.android.com/develop/ui/views/layout/recyclerview) с переиспользованием ViewHolder, стабильными ID и точечными изменениями списка. Фильтр/сортировку готовить в рабочем потоке; сохранять позицию прокрутки, фокус, выделение, доступность и состояние редактирования. Для галерей — соответствующая сетка с тем же подходом.

Это не ограничение списка первыми N людьми: все результаты остаются доступны прокруткой; меняется только число одновременно созданных UI-объектов.

## 7. Подсказки: рассчитывать оценку совпадения один раз

**Высокий приоритет, есть исполняемый эксперимент.** В `SearchSuggestions.build()` компаратор сортировки многократно вызывает `suggestionScore()` для одних и тех же имён. Оценка включает нормализацию, токенизацию и нечёткое сравнение. Затем оценка вызывается ещё раз при формировании результата.

Код: `SearchSuggestions.java:47`; `SmartPeopleSearch.java:203`, `:563`.

Улучшение первого этапа: построить массив (personId, score, исходный порядок), где score рассчитан один раз, и стабильно отсортировать его. Сохранить порядок при равных оценках. Это уже показало совпадающий top-8 на синтетических наборах и существенно меньшее время.

Следующий этап: выбирать точный top-k через ограниченную очередь вместо сортировки всего набора, но только после учёта дубликатов имён, fallback-подсказок и стабильного порядка. Не уменьшать число доступных людей и не ослаблять нечёткий поиск.

## 8. Полный поиск: индексировать подготовленный текст

**Высокий приоритет.** `SmartPeopleSearch.matchesFreeText()` для каждого человека заново соединяет имя, место, заметки и даты и нормализует текст. Поиск в шапке запускает фильтр и подсказки на каждое изменение поля. Debounce каталога не отменяет стоимость его вычислений и построения всех строк.

Код: `SmartPeopleSearch.java:418`, `:737`; `MainActivitySearch.java:62`; `MainActivityPeople.java:330`.

Улучшение: PreparedPersonSearch по ревизии человека: нормализованные имена, девичья фамилия, место, заметки, числовые даты и токены. Общий индекс дат/мест/имён для подсказок. Искомую строку разбирать один раз. Поиск выполнять вне UI, промежуточные устаревшие запросы отменять; результат применять только для актуальных ревизий запроса и дерева.

Поиск по длинным биографиям сохраняется полностью. Нечёткое сравнение нельзя заменять простым contains ради красивого бенчмарка: нужна проверка эквивалентности прежним результатам.

## 9. Проверка качества: заменить повторные обходы графовыми алгоритмами

**Высокий приоритет.** `bindState()` вызывает полную проверку качества синхронно. В анализаторе `hasRelation()` сканирует все связи для каждого человека; `relatedComponent()` сканирует все связи на каждом шаге BFS; цикл родительских связей проверяется отдельной достижимостью для каждой связи.

Код: `MainActivity.java:2646`; `MainActivityQuality.java:123`; `TreeQualityAnalyzer.java:132`, `:232`, `:334`, `:444`.

Улучшение: единый индекс смежности за O(N+E), множество людей со связями, один обход компонент. Родительские циклы определять через сильносвязные компоненты/DFS, сохраняя отображение конкретных ошибок на те же записи. Отчёт строить в рабочем потоке, кэшировать по ревизиям. Правку имени или фото проверять локально; структуру пересчитывать при изменении связей.

Все проверки и предупреждения сохраняются. Отключение проверки качества на больших деревьях в план не входит.

## 10. Раскладка: общий контекст вместо повторного построения графа

В `layoutComplete()` последовательно вызывается много проходов центрирования, уплотнения, проекций якорей и порядка ветвей. Несколько проходов повторяются. Многие из них отдельно создают FamilyLayoutGraph, LayoutSnapshot и валидатор, хотя связи между людьми на протяжении раскладки не меняются.

Код: `TreeLayoutEngine.java:116`; `BranchSlackCompaction.java:12`; `FamilyAnchorProjection.java:15`; `LineageBandReflow.java:24`; `FamilyLineageCentering.java:25`.

Улучшение: LayoutContext на одну операцию — неизменный граф родства, поколений, семей и связных компонент плюс изменяемые координаты и индексы занятости. Повторно использовать граф и списки ветвей. Проход сообщает, какие координаты изменил; следующие проходы обновляют только зависимые данные.

Не удалять повторные проходы наугад: комментарии и регрессионные тесты показывают, что они исправляют реальные геометрические случаи. Пропуск допустим при доказанном отсутствии изменений во входных данных конкретного прохода. Сохранять детерминизм, порядок братьев/сестёр, закрепления, поколения, центровку и минимальные расстояния.

## 11. Коллизии и родственные обходы: использовать индексы

В локальном исправлении перекрытий повторно запускается полный валидатор; поиск свободного сдвига сравнивает движущиеся и неподвижные карточки. В части расчётов родства для каждого посещённого человека вновь сканируется state.links. В валидаторе уже есть сортировка по X с ранним выходом: это полезно и должно учитываться, а не описываться как безусловный полный перебор всех пар.

Код: `DeterministicAdditionLayout.java:40`, `:104`; `LayoutConstraints.java:53`; `KinshipCalculator.java:197`.

Улучшение: индексы занятости по поколениям/интервалам, локальная проверка изменённых карточек с финальной полной валидацией; общий Parents/Children/Partners index для родства. Для beam-диагностики отдельно полезны кэш fingerprint и более дешёвая оценка пересечений линий, но она не выглядит главным производственным путём: реальные вызовы полной раскладки идут через детерминированный TreeLayoutEngine. Не тратить первый этап на оптимизацию неиспользуемого в обычном сценарии решателя.

## 12. Сохранение и Undo: меньше полных снимков

Перед действием History копирует TreeState. Перед записью `TreeSaveCoordinator.dispatch()` снова копирует его в UI. После сохранения онлайн-менеджер создаёт ещё одну копию. Однопоточный writer сериализует все уже отправленные снимки, даже если более новый снимок уже ожидает записи.

Код: `MainActivityHistory.java:28`, `:39`; `TreeSaveCoordinator.java:82`; `OnlineTreeManager.java:1244`.

Улучшение: единый принадлежащий операции неизменяемый снимок; разделяемые неизменяемые записи/копирование изменённых людей; команды Undo с конкретными изменениями вместо сравнения всех людей. Объединять ожидающие автосохранения текущего файла, записывая актуальный снимок после уже выполняющейся записи. Контрольные версии значимых действий и гарантии восстановления сохранять отдельно; coalescing не должен уменьшать обещанную историю пользователя.

Строки в TreeStateCopier обычно переиспользуются ссылками: это не копирование всех байтов фотографий. В локальном эксперименте копирование было намного дешевле поиска и анализа качества, поэтому его глубокая переделка имеет меньший приоритет, чем эти подтверждённые затраты.

## 13. JSON и версия файла: потоковая запись без удаления данных

Сохранение строит полное дерево JSONObject, затем форматированную строку и UTF-8 массив. Онлайн-представление повторно строит/сериализует JSON. Это увеличивает пиковую память и проходы по содержимому.

Код: `TreeStore.java:96`; `OnlineSyncPayload.java:15`; `OnlineTreeManager.java:2235`.

Улучшение: компактный внутренний формат без pretty-print; потоковый UTF-8 writer с прежней атомарной фиксацией, проверкой ошибок и восстановлением. Для внешнего JSON можно оставить форматирование по запросу. В более долгом плане — журнал конкретных изменений и периодические полные контрольные снимки, с проверяемой миграцией и восстановлением.

Не сокращать заметки, число воспоминаний, альбомов или сохранённых данных. Оптимизация размера за счёт пробелов и повторного представления отличается от обрезания информации.

## 14. Запуск приложения: загрузка и анализ вне onCreate

`MainActivity.onCreate()` синхронно вызывает `store.load()`, а затем готовит интерфейс и отчёт качества. Большое дерево задерживает первый полезный экран.

Код: `MainActivity.java:268`, `:270`, `:378`, `:2646`.

Улучшение: жизненным циклом управляемая загрузка в фоне, короткое состояние загрузки, затем применение готовой модели. Базовую подготовку индексов объединить с чтением. Не возвращать пользователя к фиктивному пустому дереву и не допускать сохранение пустого состояния до окончания загрузки. Измерять холодный старт отдельно от обычного возврата в приложение.

## 15. PNG: рисовать нужный тайл и не блокировать главный поток

**Высокий приоритет.** Экспорт создаёт отдельный TreeCanvasView, но рендер каждого тайла отправляет в UI через `imageOnUi()`. `tile()` передаёт в `drawExport()` полный crop; drawScene считает видимой всю область crop для каждого тайла. Canvas отсечёт лишние пиксели, но Java-код уже обойдёт карточки и запросит фото. В exportMode портрет декодируется заново, после рисования сразу recycle.

Код: `MainActivityFiles.java:1770`, `:1785`, `:1796`; `TreeImageExport.java:114`, `:135`; `TreeCanvasView.java:440`, `:1970`, `:1653`.

Улучшение: отделить TreeSceneRenderer от View. Один снимок и план линий на задание экспорта; в рабочем потоке рисовать software Canvas конкретного тайла. Видимая мировая область — границы тайла плюс поля для декоративных элементов. Фото переиспользовать в ограниченном по байтам кэше по mediaId и требуемому разрешению, не recycle после каждого использования.

Сохранить все стили, текст, разрешение, рамки и итоговые размеры. Проверять, что склеенные тайлы совпадают с единым PNG: одинаковая геометрия, координаты узоров, фаза эффекта и сглаживание швов. Снижение качества экспорта не предлагается.

## 16. Предпросмотр и PDF: не повторять подготовку сцены

`ExportPreviewView.refresh()` синхронно создаёт новую bitmap; настройки могут вызывать это несколько раз подряд. PDF уже рисуется в фоне, но TreeDocumentRenderer на каждой странице проходит все связи и всех людей, проверяя пересечение с областью.

Код: `ExportPreviewView.java:66`; `TreeImageExport.java:92`; `TreeDocumentRenderer.java:140`, `:154`, `:265`.

Улучшение: объединять быстрые изменения настроек, отменять устаревший preview; после отделения рендера от View — рендерить вне UI и применять только актуальную bitmap. Для PDF использовать общий пространственный индекс и подготовленные подписи/маршруты на весь документ. Не уменьшать качество окончательного файла и не менять его содержимое ради скорости preview.

## 17. Импорт: убрать двойную временную копию и тяжёлый I/O из UI

При открытии .ftree `TreeImportIO.readZip()` сначала полностью копирует архив во временный файл, а при обнаружении manifest.json/tree.json вызывает `TreePackageIO.read()`, который снова создаёт и заполняет временный файл. Это лишнее чтение/запись всего архива и дополнительное свободное место.

Код: `TreeImportIO.java:62`, `:80`; `TreePackageIO.java:83`.

Улучшение: единый staged-архив с проверенными границами, из которого .ftree/GEDCOM-ветка читает напрямую. Поддержать отмену в циклах чтения. Добавление фото и memory-вложений через onActivityResult перенести из главного потока, оставив в UI проверенное применение результата.

Дедупликация бинарных файлов по хешу уже есть; не заменять оригиналы сжатыми копиями и не обрезать архивы под искусственно меньшие лимиты.

## 18. Онлайн: разделить состояние дерева, медиа и повторную сериализацию

Один scheduled worker обслуживает синхронизацию и передачу медиа. Длинное видео/повтор загрузки может задерживать очередь других операций. `onLocalTreeSaved()` повторно сериализует дерево, `sameJson()` каждый раз парсит обе строки и снова сериализует их для сравнения. При обычном pull после получения файла media download может предшествовать передаче нового дерева в интерфейс; начальное restore уже использует более отзывчивую последовательность.

Код: `OnlineTreeManager.java:181`, `:1241`, `:1755`, `:1761`, `:1780`, `:1908`, `:2270`.

Улучшение: сериализуемый управляющий поток для состояния/ревизий и отдельно ограниченная очередь медиа; актуальные снимки и метаданные не должны ждать всей передачи большого файла. Применение структуры после безопасной проверки и сохранения локальных правок, затем фоновые медиа с прогрессом. Кэшировать канонический документ/хеш общей части дерева и список ссылок на медиа. Хеш не должен исключать какие-либо пользовательские поля или ослаблять трёхстороннее объединение.

Не запускать неограниченные параллельные запросы: необходимы порядок ревизий, лимиты памяти, отмена по смене сессии, backoff и уважение ограничений сервера.

## 19. Виджеты: не загружать полное дерево для каждого типа после каждой записи

После сохранения вызывается BirthdayWidgetProvider.updateAll(). Для каждого установленного пресета ставится задача, которая самостоятельно загружает TreeStore, затем вычисляет ближайший день рождения. При четырёх типах виджетов одна ревизия может приводить к нескольким чтениям одного файла. Уже есть защита от устаревших обновлений, но не от всех повторных загрузок одной актуальной ревизии.

Код: `MainActivity.java:368`; `BirthdayWidgetProvider.java:65`, `:91`.

Улучшение: один неизменяемый снимок/индекс нужных виджету полей на ревизию и одно задание для всех размеров. Обновлять выбор даты при изменении рождения, статуса, имени, фото, исключений либо наступлении нового дня. Перетаскивание карточек и изменение цвета не требуют повторного разбора всех биографий.

## 20. HTML-экспорт и выпускная сборка

Уточнение после повторной проверки: redraw уже объединяет события через requestAnimationFrame. Повторный вызов из pinch сам по себе не означает второй рендер кадра. При этом полные проходы людей/связей и измерение текста повторяются, а поиск заново собирает нормализованные строки.

Код: `app/src/main/assets/tree-export.html:33`, `:35`, `:41`, `:42`, `:47`.

Улучшение: сохранить существующее объединение через requestAnimationFrame, добавить подготовленные подписи и индекс поиска, пространственный индекс и переиспользуемую геометрию. Все данные автономного HTML должны оставаться доступны.

**Уже существующее урезание по масштабу:** в HTML есть `if(zoom<.16)continue`, которое пропускает содержимое карточки после её рамки. В native-коде отдельные маркеры зависят от порогов `scale`. Это текущая реализация, а не рекомендация настоящего плана. Если требуется одинаковый набор деталей на всех масштабах, такие условия нужно отдельно убрать и проверить читаемость/производительность через кэши, а не вводить новые отсечения.

В release сейчас `minifyEnabled false` и `shrinkResources false`. Отдельным экспериментом можно проверить R8 и удаление действительно неиспользуемых ресурсов, с тестированием рекламного SDK, аналитики, reflection и всех экранов. Это потенциально уменьшает установку/загрузку кода, но не заменяет исправление горячих циклов. Для фоновой PNG-текстуры и шрифтов допустима лишь доказанно эквивалентная обработка: lossless-оптимизация и сохранение всех необходимых символов/начертаний; размер выигрыша пока не измерен.

## План выполнения и критерии приёмки

**Первый этап: заметная польза при ограниченном вмешательстве.**

1. Однократный score подсказок, подготовленный поисковый текст, отмена устаревших запросов.
2. Переработка обходов TreeQualityAnalyzer и фоновый расчёт отчёта.
3. RecyclerView для каталога/галерей с прежними результатами и доступностью.
4. Ревизии кэшей семейных линий и CardRenderData.
5. Устранение двойного staging .ftree и синхронного импорта вложений.

**Второй этап: рендер и большие задания.**

6. Отдельный renderer для PNG, точная область тайла, общий кэш экспортных фото.
7. Общая очередь фото с приоритетами и бюджетами памяти.
8. LayoutContext и переиспользование графа между проходами без изменения результатов раскладки.
9. Объединение работы сохранения, онлайн-синхронизации и виджетов по ревизиям.

**Третий этап: изменения форматов и выпуска.** Потоковый внутренний JSON, журнал изменений/контрольные снимки, R8 и профили запуска — после замеров и проверки восстановления.

Проверять на release/profileable-сборке, как рекомендует [руководство Android по медленной отрисовке](https://developer.android.com/topic/performance/issues/render). Бюджет кадра зависит от частоты экрана: примерно 16,7 мс при 60 Гц, 11,1 при 90 и 8,3 при 120. Измерять frame time p50/p95/p99 и пропущенные кадры, время поиска и открытия каталога, холодный старт, peak Java/native bitmap memory, GC, число декодирований фото, байты дисковых записей и сетевых передач.

Наборы: 100/500/2000/5000+ человек; широкие семьи, глубокая цепь, повторные браки, циклы некорректного импорта, тысячи фото, длинные биографии, большой видеофайл. Сценарии: дальний общий вид и полный набор деталей, pinch/pan, перетаскивание, массовое выделение, поиск с опечатками, каталог/альбомы, Undo/Redo, сохранение и перезапуск, PNG/PDF/HTML, импорт и синхронизация при медленной сети.

Главный критерий: результаты поиска и анализа, количество записей/фото/связей, качество файлов и геометрические инварианты совпадают. Поэкранные сравнения делать при нескольких масштабах и стилях. Ускорение за счёт пропажи информации считается регрессией.
